# Phase 1: independent verification of Experiment 01 (BCM-01)

Date: 2026-10-26. Scope: the 9,191-trajectory cohort of Raichura & Banerjee (arXiv:2608.13598) as
re-assembled in `bcm-validity/` (git 63da902). I checked the Exp01 claims against raw source
shards, the authors' shipped artifacts and the authors' git history. I did not take the Exp01
reports as ground truth. No Exp01 file was modified. All verification code is in `scripts/`, outputs
are in `results/`, Slurm logs are in `logs/`. Environment: `bcm-validity/.venv` (Python 3.11,
LightGBM 4.7.0, shap 0.51.0, scikit-learn as in `bcm-validity/requirements.lock`). No model API
calls, cost $0.

Labels: **CONFIRMED** = reproduced from raw data or independent code. **CORRECTED** = Exp01's
statement was wrong or incomplete, and the corrected statement is given. **RESOLVED** = an issue
that Exp01 left open is now explained. **UNRESOLVED** = still open.

## 1. The paper's numbers come from a leaky, early-stopped model (V7)

Clues in the shipped files:
- The implied per-row base value `logit(p) − Σφ` takes exactly 5 values (folds of 1,838/1,839 rows).
  These folds equal `StratifiedKFold(5, shuffle=True, random_state=42)` on our labels in our row
  order. Labels and order were therefore correct, and the model differed.
- The SHAP for `consecutive_repetition_max` is exactly 0 on all rows, while the feature takes 20
  distinct values. 198 groups of identical SHAP vectors appear on rows with different features, which
  points to very coarse trees.
- `results/unified_shap_predictor_output.txt` prints "TOP FEATURE IMPORTANCES (NORMALIZED GAIN)".
  The released script never prints this; `model/predictor.py@48fcfd0` does.

`scripts/v7_shipped_model_search.py` takes the 48fcfd0 hyperparameters (1,500 trees, lr 0.005, 15
leaves, depth 4, colsample 0.8, min_child_samples 30, L1 2, L2 10, `scale_pos_weight` = neg/pos),
fits with `eval_set=[(X_val, y_val)]` and `early_stopping(50)`, then applies tree-path TreeSHAP.
On the authors' own feature CSV this gives:

| | pooled AUC | max \|Δproba\| vs shipped | max \|ΔSHAP\| vs shipped | best iteration per fold |
|---|---|---|---|---|
| released script (200 trees) | 0.728 | 0.53 | 2.20 | 200 ×5 |
| **48fcfd0 + early stop on validation fold** | **0.690** | **0.0** | **0.0** | **173, 225, 66, 82, 4** |
| 48fcfd0, no early stop | 0.732 | 0.55 | 1.56 | 1500 ×5 |
| 48fcfd0 + early stop, no `scale_pos_weight` | 0.695 | 0.26 | 0.86 | 29, 20, 6, 58, 90 |

The validation-fold early stopping is leaky, but it *lowers* the pooled AUC (0.732 → 0.690). Stopping on noisy per-fold AUC peaks selects very small models. The paper's AUC 0.690 understates what the same features support, and the paper's BCMs come from these under-fitted models.

Consequences:
1. **Evaluation leakage.** The tree count is chosen on the fold being scored, so AUC 0.690 and every
   out-of-fold SHAP vector depend on validation labels.
2. **Heterogeneous attribution models.** One fold's attributions come from a **4-tree** model. Pooled
   BCM averages cosines across folds whose models differ by 50× in size. Per-fold BCM
   (`results/v7b_fold_decomposition.csv`): GPT-4o 0.953 in the 4-tree fold vs 0.718–0.818 elsewhere;
   excluding that fold moves GPT-4o from 0.814 to 0.771. Other systems move ≤0.017.
3. The paper text and the released code describe a configuration that did not produce the published
   numbers. This is a reporting discrepancy to raise with the authors. It is neither fabrication nor
   an unexplained artifact.

## 2. Label-permutation negative controls, 50 pre-specified seeds (V5)

Independent pipeline `scripts/v5_independent_pipeline.py`. Seeds 1000–1049, fold seed 42. Additivity
is asserted <1e-6 on every validation row of every fit (observed max 0.0 for linear, ≤1e-13 for
trees). Three predictors: `paper_code` (released script), `paper_actual` (V7 configuration,
reproduces Table 2) and `logistic`. Three nulls: within system (preserves prevalence), within
system×repository (preserves repository-level success rates), and global.
Full table: `results/v5_permutation_summary.csv`; separations: `results/v5_separation_summary.csv`.

Selected rows (real BCM; within-system null median [5%, 95%]; add-one one-sided p that real ≤ null):

|---|---|---|---|---|---|---|
| author / paper_actual (= published) | 0.832; 0.955 [0.744, 0.974] | 0.765; 0.955 [0.755, 0.976] | 0.814; 0.718 [0.422, 0.881] | 0.071; 0.728 [0.576, 0.851], p=0.02 | 0.065; 0.757, p=0.02 | 0.086; 0.748, p=0.02 |

| role-aware / paper_code | 0.435; 0.516, p=0.04 | 0.516; 0.668, p=0.02 | 0.254; 0.373, p=0.04 | 0.109; 0.338, p=0.02 | 0.132; 0.384, p=0.02 | 0.109; 0.321, p=0.02 |

p=0.02 is the minimum attainable with 50 permutations.

Findings:
- **Under the configuration that produced the paper, models trained on outcome-shuffled labels give the
  Claude systems *higher* BCM (median 0.955) than the real labels do.** The published proprietary
  values are therefore not evidence of success-relevant consistency.
- Under the role-aware parser, real-label BCM is below the within-system null in 17 of 18
  system×predictor cells (p ≤ 0.04). The exception is logistic / Claude-3.5 (real 0.436 > null
  median 0.329). Real outcome information *lowers* BCM. BCM is high when the predictor has nothing
  system-specific to learn, because attributions then collapse onto source-identifying features.
- **New null (system×repository).** With labels shuffled only within repository, the
  proprietary–Llama separation largely persists: author/paper_code S = 0.381 [0.279, 0.443] vs real
  0.487; paper_actual 0.372 vs 0.679. Most of the published group separation needs no within-repository
  outcome signal at all.
- Within-system null AUC is 0.57–0.63 > 0.5 in every configuration, because system identity predicts
  prevalence. The global null is at chance (0.497–0.502).

## 3. SHAP explainer correctness (V6, V6b, V6c)

- Tree-path TreeSHAP (the paper's explainer): |Σφ + E − margin| ≤ 1.8e-14 on all rows, both parsers,
  all predictors. **Valid.**
- `TreeExplainer(data=bg, feature_perturbation="interventional", model_output="raw")` with shap 0.51
  and LightGBM 4.7: Σφ + `expected_value` = margin (additive to its own base), but `expected_value` −
  mean background margin = **0.1312 (author)** and **0.0408 (role-aware)** on fold 0 / background seed 211.
  The constant offset hides the error from a standard additivity check, and the attributions are wrong.
  Rounding features to float32 does not remove it, so a float32 threshold mismatch is not the cause.
  **Root cause RESOLVED 2026-11-03 (V6d, V6e; `results/v6d`, `results/v6e`): not a numerical bug.**
  `TreeExplainer(model, data=bg)` wraps `bg` in `shap.maskers.Independent(bg)`, whose default
  `max_samples=100` silently subsamples any larger background. With our 128-row background shap
  explained against a random 100-row subset: its `expected_value` equals the LightGBM mean margin over
  those 100 rows exactly (0.0), and its attributions equal brute-force exact interventional Shapley
  values over the 100 rows (max dev 6e-8 author, 1.2e-4 role-aware). Passing
  `maskers.Independent(bg, max_samples=len(bg))` removes the offset (0.0) and the deviation from exact
  values over all 128 rows (6e-8 / 9e-5). V6d also ruled out tree-conversion errors: shap's internal
  trees reproduce LightGBM on every row and tree (0 mismatches; `<` vs `<=` irrelevant). The residual
  ≤1.2e-4 on role-aware rows is unexplained and immaterial. Nothing to report upstream as a math bug;
  at most a usability issue (no warning when the background is subsampled).
- Ground truth: brute-force exact interventional Shapley over all 4,096 coalitions
  (`v6_shap_additivity.exact_interventional`). It equals `shap.explainers.Exact` to 1.7e-14 and is
  additive to 5e-15. TreeExplainer-interventional deviates by up to 0.096 per feature on 20 checked rows.
- Corrected stage G (`v6c_exact_interventional_full.py`): exact values for all 9,191 rows × 3 Exp01
  backgrounds × 2 parsers, additivity <1e-8 asserted (`results/v6c_corrected_G.csv`).

## 4. What changes in the Exp01 conclusions

1. "Cause unknown" for the reproduction gap → **explained** (V7). The paper's Table 2/3/4 values rest on
   a model selected on validation labels, one of whose folds has 4 trees.
2. The within-system null argument is **stronger** than Exp01 stated: under the paper's actual model the
   null *exceeds* the real proprietary BCMs.
3. The SHAP-additivity issue is **reclassified** as an explainer defect affecting both parsers, with
   negligible BCM impact. It is not a data property of the role-aware features.
4. Within- vs between-task: the "+0.2 within-task" pattern is **not Llama-specific**. It appears for
   Claude once parsing is corrected.
5. Unchanged: zero-step bug, parser asymmetry, magnitude sensitivity to parser and predictor, logistic
   separation ≈ 0, ordering robustness to folds and tree hyperparameters.

## 5. Unresolved

- Root cause of the shap 0.51 interventional offset (upstream report pending).
- Human annotation: `results/v4_human_review_sheet.csv` (24 rows) needs a human annotator. Exp01's
  60-record validation was done by the AI agent and is **not** human validation.
- Whether the authors' paper-run environment used another LightGBM version. Not needed: bit-exact
  reproduction with 4.7.0.
- Exp01's confound (source = scaffold = task set = parser = model family) cannot be resolved with this
  cohort. Exp02 addresses it on a single benchmark and scaffold.
